Phaselock Timer

A productivity app that combines time-block planning with work/rest rhythm (Pomodoro). Define a time block, set work and break durations, and let the app distribute cycles automatically.

Stack: Spring Boot 4.0, Java 21 LTS, WebSocket (STOMP), JavaScript, RESTful API, Web Audio API, Browser Notifications, Git — DTO, Service Layer, Repository pattern

Executive summary

Phaselock Timer is a full-stack productivity application that integrates time-block planning with the Pomodoro technique. You define how long you want to work on a task, configure work and break durations, and the app automatically distributes cycles and notifies you when to switch. Real-time updates and native browser notifications keep you on track without constantly checking the screen.

The process: how I built it

Identifying the problem

Many people struggle to structure their workday: either working non-stop without rest or taking breaks without a clear plan. Manually switching between focus and rest is distracting, and rigid timers often don't fit the time you actually have. I wanted an app that would let me define a time block (e.g. two hours), set work and break intervals, and handle the distribution automatically—so I could focus on the task instead of managing timers.

Defining scope and tools

I chose a web app for cross-device access. Spring Boot 4 on the backend provides a RESTful API, dependency injection, and WebSocket support for real-time sync. The frontend uses vanilla JavaScript with the Web Audio API for sounds and the Browser Notifications API for alerts, avoiding polling. The goal was simplicity: start a session, configure durations, and let the app handle the rest. Git supported version control throughout.

The design process

The starting point

Given the nature of this project, I started by sketching wireframes and deciding the best strategy to combine Pomodoro and time blocking in one timer. That process shaped the technologies I would need and became the starting point for researching how to implement them and for designing the architecture.

Designing the architecture

I started by splitting the problem into block configuration and timer execution. On the backend I kept responsibilities separate: controllers only handle HTTP, services hold the logic, repositories handle persistence, and DTOs define the API contract without exposing entities. When the UI needed live updates, I compared polling with WebSocket and went with WebSocket (STOMP) so the server could push state changes. The frontend stayed in vanilla JavaScript to keep the stack simple and to use WebSocket, the Web Audio API, and browser notifications directly.

Designing the UX/UI

I started by sketching wireframes by hand, then refined the flow: set the time block, choose work and break durations, start the session, and follow the prompts. The main screen shows the current phase (work or break) and the countdown. Notifications and sound cues indicate when to switch. I kept the layout minimal so the user could focus on the task rather than the interface.

Implementation and results

The application was built in stages: first the backend (REST API for blocks and timer, JPA entities, services, and repositories), then the web UI that consumes that API, then WebSocket for real-time updates instead of polling, and finally notifications (sounds via Web Audio API and browser notifications when the tab is in the background). The result is a working product where the user can create and configure time blocks, run the timer with pause/resume/skip, see live countdown and phase changes, and get audible and visual alerts. All requirements from the initial spec were covered, and the codebase is structured so that new features (e.g. user accounts or persistence to a file/DB) can be added without reworking the core.
